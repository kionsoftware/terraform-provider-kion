# Terraform Provider for Kion

A Terraform provider for the [Kion](https://kion.io) cloud governance platform, built on the [Terraform Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework).

## Overview

Generated from the Kion OpenAPI specification, this provider manages 75 service packages covering organizational management, cloud access, compliance, financial governance, and more. Almost everything is generated: resource CRUD, schemas, data sources, acceptance-test scaffolding, `.tf` examples, registry docs, and a Terraform module per resource.

The provider is built against a single Kion API version, the SDK's `generated/v3_17` sub-package. It does not ship a separate release line per Kion version. Compatibility with older self-hosted instances is handled at runtime instead: `codegen/version_support.yaml` records the Kion version range in which each resource's defining API operation exists, and resources whose operation is not present in every supported version carry a generated version gate that fails with a clear diagnostic when pointed at an instance too old to support it.

## Importing an existing install

`kion-import` reads a live Kion install and writes Terraform `import` blocks;
`terraform plan -generate-config-out` then writes the configuration. See
**[docs/guides/importing.md](docs/guides/importing.md)**, which covers choosing what to import,
because a real install carries tens of thousands of records in Kion's shipped
catalogs.

## Upgrading from the previous provider

Coming from the SDKv2 `kion` provider? State migrates automatically; configuration
needs a rewrite, which [`kmigrate`](cmd/kmigrate) does for you and which ships as
a binary on every release. **[docs/guides/upgrading-from-0.3.md](docs/guides/upgrading-from-0.3.md)** is the
procedure, and [docs/MIGRATION-COVERAGE.md](docs/MIGRATION-COVERAGE.md) records
what is covered.

## Provider configuration

```hcl
terraform {
  required_providers {
    kion = {
      source = "registry.terraform.io/kionsoftware/kion"
    }
  }
}

provider "kion" {
  api_url = "https://your-kion-instance.com"  # or KION_API_URL
  api_key = var.kion_api_key                  # or KION_API_KEY
}
```

An app API key is all you need. `api_key` is sent as `Authorization: Bearer <value>`.

<details>
<summary>Other accepted attributes</summary>

| Attribute | Notes |
|---|---|
| `auth_token` / `KION_AUTH_TOKEN` | Accepted, but not a distinct credential type. It is sent as the same `Authorization: Bearer <value>` header as `api_key`, and `api_key` wins if both are set. Prefer `api_key`. |
| `skip_ssl_validation` / `KION_SKIP_SSL_VALIDATION` | Skip TLS verification. |
| `url`, `apikey` | Deprecated aliases carried over from the previous provider. Use `api_url` and `api_key`. |
| `apipath` | Base path appended to `api_url`, defaulting to `/api`. Same meaning as in the previous provider, including `apipath = ""` to address an API mounted at the root. Rarely needed. |

Configuration fails if neither `api_key` nor `auth_token` is supplied, and if `api_url` is missing.
</details>

## Architecture

### Service package pattern

Each Kion resource lives in its own package under `internal/service/<name>/`:

```
internal/service/label/
  label.go                     # Resource CRUD (generated by kgen crud)
  label_schema_gen.go          # Schema + model (generated from the OpenAPI spec)
  label_data_source.go         # Data source
  label_version_gen.go         # Kion version gate, when the resource needs one
  label_test.go                # Acceptance tests
  service_package.go           # Factory registration
```

Resources embed `framework.ResourceWithConfigure` (data sources embed `framework.DataSourceWithConfigure`), which inject the shared `KionClient` from the provider's `Configure` method.

**Generated files carry a `// Code generated by kgen …  DO NOT EDIT.` header. Edit the codegen inputs, not the output.** See [Code Generation](#code-generation).

### Directory structure

```
.
├── cmd/
│   ├── kgen/                   # Code generator CLI (schemas, crud, modules, examples, tests)
│   ├── kmigrate/               # Rewrites configurations written for the previous provider
│   ├── kconfig/                # Derives codegen/generator_config.yaml from the service packages
│   ├── kalign/                 # Schema/SDK alignment checks
│   └── kversions/              # Derives codegen/version_support.yaml from the SDK
├── codegen/                    # Hand-maintained generator inputs (see Code Generation)
├── internal/
│   ├── acctest/                # Acceptance test helpers
│   ├── conns/                  # KionClient wrapper, raw HTTP for endpoints the SDK lacks
│   ├── errs/                   # SDK response -> diagnostics helpers
│   ├── flex/                   # Type converters: TF <-> SDK
│   ├── framework/              # Base types, Kion version gates
│   ├── kgen/                   # Generator implementation and templates
│   ├── provider/               # Provider definition and registration
│   ├── provider_kion/          # Generated provider schema (from tfplugingen)
│   ├── service/                # 75 service packages, plus accounthelper (shared, not a package)
│   └── servicepkg/             # Shared registration types
├── spec/                       # gitignored: local codegen input, fetched by make refresh-spec
├── modules/                    # 72 generated Terraform modules (one per resource)
├── examples/                   # Generated .tf examples (resources, data sources, provider)
├── docs/                       # Registry documentation (tfplugindocs)
├── .github/workflows/          # GitHub Actions: ci.yml gates, release.yml publishes
├── .golangci.yml               # Linter config
├── .goreleaser.yml             # Release artifact layout (Terraform Registry)
├── lefthook.yml                # Pre-push git hooks
└── Makefile                    # build, test, lint, CI, install, codegen
```

### SDK integration

The provider uses [kion-sdk-go](https://github.com/kionsoftware/kion-sdk-go), a typed Go SDK generated from the Kion OpenAPI spec with [ogen](https://ogen.dev/). Resource code imports the `generated/v3_17` sub-package, aliased `generated`.

Type conversion between Terraform Framework types (`types.String`, `types.Int64`, …) and SDK types (`generated.OptString`, `generated.OptUint64`, …) lives in `internal/flex`.

`go.mod` requires `github.com/kionsoftware/kion-sdk-go` at a tagged version, which the module proxy resolves like any other dependency. **A plain clone builds with no sibling checkout**, and a release builds from exactly the version `go.mod` pins.

**`spec/openapi3.json` is not committed.** It is gitignored. This repo is published for customers and ships the provider, not Kion's interface files. Because the generated code *is* committed, a plain clone still builds, tests, and regenerates modules, docs, and examples with no spec present.

Only the two schema generators read it (`make generate-schemas`, `make config-gen`), and `make refresh-spec` fetches a local copy from the SDK spec source (maintainers only). Point `SDK_SPEC_ROOT` at that source's `spec/` directory, in the environment or a gitignored `local.mk`, or pass `SDK_SPEC=<path>` for the file itself. `SDK_VERSION` in the Makefile (`v3_17`) is the Kion version the provider targets and selects both the spec and the `generated/<v>` sub-package the code imports.

A few endpoints the public spec does not expose are served over raw HTTP through `internal/conns`; those are declared in `codegen/private_endpoints.yaml`.

## Code generation

Nearly the whole provider is generated. The inputs live in `codegen/` and are the files to edit. **[`codegen/README.md`](codegen/README.md) is the guide**: what each input does, the invariants, and the traps that have cost real time.

| File | Purpose |
|---|---|
| `generator_config.yaml` | Per-resource CRUD paths driving schema generation (derived; see `config_overrides.yaml`) |
| `config_overrides.yaml` | Hand-tuned paths `kconfig gen` cannot derive |
| `schema_overrides.yaml` | What the spec cannot express: descriptions, plan modifiers, type changes, attribute removal |
| `crud_archetypes.yaml` | Which CRUD shape each resource uses (entity, blended, association, parent_list, …) |
| `private_endpoints.yaml` | Endpoints absent from the public spec, plus their read shapes |
| `renames.yaml` | Attribute renames |
| `version_support.yaml` | Kion version ranges per resource (derived by `kversions`) |
| `test_values.yaml` | Sample values for generated acceptance tests |

```bash
make refresh-spec             # Fetch the OpenAPI spec locally (needs the kion-sdk monorepo)
make generate                 # version gates + schemas + CRUD
make modules                  # Terraform modules + terraform-docs injection
make examples                 # .tf examples
make docs                     # Registry docs (tfplugindocs)
```

`make crud` and the other generators **skip files that already exist**. Pass `--force` to regenerate:

```bash
go run ./cmd/kgen crud --force                    # all resources
go run ./cmd/kgen crud --resource label --force   # one resource
```

Scaffolding a brand-new service package:

```bash
go run ./cmd/kgen service --name CloudRule --snakename cloud_rule
```

Then add its entries to `codegen/` (paths, archetype, and a read shape if the read is private) and regenerate.

> Adding or removing a resource changes four generated trees: `internal/service/`, `examples/`, `docs/`, and `modules/`. Regenerate all four; CI has a drift gate on `modules/` (`make modules-check`) and on `docs/` + `examples/` (`make docs-check`), so a missed regeneration fails the build rather than shipping stale documentation. It also changes the supported surface tracked by the sibling `terraform-coverage-test` project; run `make coverage-new` there and add modules for anything newly reported as a gap.

## Development

### Prerequisites

- [Go 1.25.13](https://go.dev/doc/install), the version `go.mod` pins
- [golangci-lint v2](https://golangci-lint.run/welcome/install/)
- [lefthook](https://github.com/evilmartians/lefthook) (git hooks)
- The SDK is resolved from the module proxy, so no sibling checkout is needed. Regenerating schemas also needs a local SDK spec (`SDK_SPEC`)
- `make install-codegen-tools` installs pinned tfplugingen-openapi, tfplugingen-framework, and tfplugindocs
- Terraform 1.15.9 and `terraform-docs` 0.24.0, for the module tests (the versions `ci.yml`'s `modules` job pins)

### Common commands

```bash
make build                    # Build provider binary
make test                     # Unit tests with coverage
make testacc                  # Acceptance tests (needs a live Kion + credentials)
make fmt
make lint
make vet
make ci                       # every CI check that can run locally
make ci-quick                 # fmt, vet, lint, test only, for iterating
make install                  # Build + copy to ~/.terraform.d/plugins/
```

`make ci` runs every `ci.yml` job except CodeQL, which only runs on GitHub. That includes the two drift gates, `ci-docs` and `ci-modules`, so a schema change that leaves `docs/` or `modules/` stale fails locally instead of after a push. It regenerates and installs pinned tools, so it takes a few minutes; `make ci-quick` is the fast subset for the inner loop.

Lefthook runs `ci-fmt`, `ci-vet`, `ci-lint`, and `ci-test` as a pre-push hook, the same four targets as `make ci-quick`. Note that a **tag-only** push matches no changed files, so lefthook skips them; release tags are gated by `ci.yml` on the pushed commit, not by the hook.

### Testing the generated modules locally

`modules` is the CI job most likely to catch a regression, and it is reproducible locally. It builds the provider into a filesystem mirror, regenerates the modules to a scratch directory, then runs `terraform fmt -check`, a drift diff against `modules/`, `terraform validate`, and `terraform test` over every module. `make ci-modules` is the local equivalent. See the job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml); running the same steps locally beats waiting on CI to tell you.

## CI/CD

GitHub Actions is the only pipeline. Two workflows, documented in detail in [`.github/workflows/README.md`](.github/workflows/README.md).

### `ci.yml` gates changes

Runs on pull requests and pushes to `main`. Every job runs in parallel, and the `ci` job is a required-status aggregator that fails if any of them did, so branch protection only needs to require that single check.

| Job | What it enforces | Local equivalent |
|---|---|---|
| `fmt` | `gofmt -s` is clean | `make ci-fmt` |
| `vet` | `go vet ./...` | `make ci-vet` |
| `lint` | `golangci-lint` v2 | `make ci-lint` |
| `test-unit` | Unit tests, race detector, coverage | `make ci-test` |
| `acctest-config` | Acceptance-test HCL matches the provider schema | `make ci-acctest-config` |
| `docs` | `docs/` and `examples/` are not stale | `make ci-docs` |
| `modules` | Generated modules build, validate, test, and are not stale | `make ci-modules` |
| `internal-refs` | No internal paths or hostnames in tracked files | `make ci-internal-refs` |
| `secrets` | Credential scan over the tree | `make ci-secrets` |
| `codeql` | CodeQL analysis for Go | GitHub only |

No SDK checkout step is needed: the module proxy resolves the version `go.mod` requires.

### `release.yml` publishes

| Trigger | Purpose |
|---|---|
| Tag push (`v*`) | goreleaser → GitHub release in the layout the Terraform Registry requires |

## Versioning and releases

**The provider's version is its own. It does not track Kion's.** Encoding the Kion release in the provider version leaves nowhere to put a provider patch: a fix for the provider against Kion 3.16.4 has no number available, and `~> 3.16` would read as a Kion pin while behaving as a provider pin.

Kion compatibility is a **runtime** mechanism instead. The provider reads `GET /api/version` at configure time and gates each resource against the Kion range its defining API operation exists in (`codegen/version_support.yaml`), failing with a clear diagnostic rather than a confusing API error. The supported window mirrors the SDK's: the current Kion release and three back.

| Change | Bump |
|---|---|
| Provider bug fix | patch, any time, independent of Kion |
| New Kion release adds resources or attributes | minor |
| A provider resource or attribute is removed or renamed | major |

Releases come off `main`; there are no per-Kion release branches. If a released line ever needs a back-patch, branch `release/<provider-major>.x`, keyed to the provider's major and never to a Kion version.

### Changelog

Entries are YAML fragments under `.changes/unreleased/`, one per change, so concurrent pull requests never conflict on `CHANGELOG.md`. `CHANGELOG.md` holds released versions only.

```bash
make changelog-new        # add an entry for your change (interactive)
make changelog-preview    # what the next release notes would say
```

### Cutting a release

```bash
make release-prepare RELEASE_VERSION=1.0.0   # make ci, then batch fragments into CHANGELOG.md
git add .changes CHANGELOG.md && git commit -m "release 1.0.0"
git tag -a v1.0.0 -m v1.0.0 && git push origin main v1.0.0
```

The tag is the version. Nothing in the repo records it. `make version` reports the latest release tag (`0.0.0-dev` on an untagged tree), and that is what `make install` uses for the local plugin path. `make release-snapshot` builds the real artifact set locally without publishing.

The tag triggers `release.yml`, which builds with goreleaser, signs `_SHA256SUMS` with the release GPG key, and attaches the registry manifest, the exact artifact set the Registry requires. Release notes are the changie version file for that tag.

Publishing needs two repository secrets: `GPG_PRIVATE_KEY` (the ASCII-armoured private key) and `PASSPHRASE` (its passphrase), with the matching public key registered on the Registry provider page.

`github.com/kionsoftware/kion-sdk-go` resolves from the module proxy, so the release workflow needs no SDK checkout, and the build uses exactly the version `go.mod` pins. Do not reintroduce a clone step: a branch checkout would silently override that pin and make the release unreproducible.

## Contributing

1. Create a branch from `main`
2. Make changes and ensure `make ci` passes
3. Regenerate any affected generated surfaces (see [Code Generation](#code-generation))
4. Run `make changelog-new` if the change is user-visible
5. Open a pull request

For new resources, scaffold with `kgen service`, add the `codegen/` entries, and regenerate. Do not hand-write CRUD.
